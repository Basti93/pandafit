# Pandafit Run Coach Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An optional run coach per profile. It reads runs from Garmin or from manual entry, plans the week (get fit again first, then distance), shows healthy progress numbers, and sends planned runs to Garmin only after confirmation. It runs in the coach runtime on the Mac and on the home server, and the phone and Mac show the same screens.

**Architecture:** A new `RunCoach` lives in `src/coach/run/` and is wired into `createCoachRuntime`, so the Mac and the server run the same code. All run data travels as records of a new kind `run`. The coach writes `week-*`, `status` and `review-*` records. Phone and Mac write `settings`, `manual-*` and `send-*` records. One shared React screen in `src/tracking/ui/` works on both devices through `TrackingPort`, so the coach protocol gets no new messages. Pure modules (FIT reading, day hardness, numbers, rules, guardrails) carry the logic. The coach class only gathers inputs, plans, asks Claude within limits, and exports records.

**Tech Stack:** TypeScript, vitest, React 19, `node:sqlite` (read-only Garmin DB), `node:zlib` (`inflateRawSync` for the FIT zip), `@garmin/fitsdk` (already a dependency), zod, Python 3 with the installed `garminconnect` 0.3.20, Fastify web-server with Web Push.

**Spec:** `docs/archive/specs/2026-11-03-run-coach-design.md` (the section "Settled after the builder check" is binding)

## Global Constraints

- "Public repo: no names, real run data, tokens or hostnames in commits, tests or docs." Test fixtures use made-up ids (`pa`), synthetic FIT files built in the test, and `example.invalid` URLs.
- "Garmin stays optional, and there is a test for "not there"." Every integration (Garmin data, Garmin send, Claude) has a test that it is missing and nothing breaks or shows.
- "German text without guilt, pressure, streaks or comparisons, and without medical conclusions." Use correct umlauts (ä ö ü ß), and a decimal comma for numbers. Never write "Rekord", "Serie", "Streak", "musst" or "Pflicht", never compare to other people, and never name a diagnosis.
- Anti-goal: "the app never asks for a new record on an ordinary run." Best times appear only for planned test runs.
- Anti-goal: "A person without Garmin, or one who does not run, sees anything of this." The only exception is the "Laufen" switch in profile settings (Ruling 11).
- "A ride is never lost." `src/service/**` and `src/main/**` are not touched. `src/shared/**` changes (`records.ts`, new `run.ts`) are made only while no ride is open. Never run `npm install`, `npm run app` or a coach restart during an open ride. No new npm dependency is needed.
- "Nothing is sent without confirmation", and a changed sent run needs a new confirmation. Nothing goes to Garmin while a ride is open.
- "The bike coach never creates strength workouts." The run coach creates no bike or strength workouts. It only reads other coaches' plan data and never changes their decisions.
- New coach logic lives in or under `createCoachRuntime` (`src/coach/runtime.ts`), never in `src/coach/main.ts` or `src/coach/server/*`.
- When Claude is unavailable the rule plan stands. Claude runs only with no ride open, through the runtime's `ask` (the server already serializes it via `HeavyLock`).
- Verification for every task: `npx vitest run <test files>` and `npm run typecheck`. Python: `npm run test:garmin`. Commits use the `feat(run):` / `fix(run):` prefix and end with the session's attribution lines.

## Review Focus

- A run recorded by the watch and also entered by hand, or a watch whose clock is a few minutes off: it counts once, the Garmin one wins, and weekly kilometres do not double (Task 3: `a manual run overlapping a Garmin run by half counts once`, `two minutes clock drift still merges`).
- A phone that last synced before `run` existed: its cursor already moved past `run` records, so it must refetch everything once, or it never shows the plan (Task 2: `a cursor stored under the old kinds signature starts from 0 again`).
- "An Garmin senden" tapped twice, on two devices, or right before the plan changes or a ride opens: no duplicate workouts on the watch, old ones are deleted before new ones, nothing goes out during a ride, and a stale confirmation sends nothing (Task 10: `a send record is handled once`, `an old fingerprint marks stale`, `a ride open waits`).
- A broken or partial FIT: a truncated zip, no `.fit` inside, no heart-rate strap, GPS dropouts with speed 0 or gaps of minutes. The run still counts for kilometres and time, gets no easy pace, and nothing throws (Task 1: `a truncated zip gives null`, `gaps over 5 s are not counted`, `zero speed seconds are not counted`).
- Week edges: a run at 23:30 on Sunday, a week with a daylight-saving change, a server in another time zone. Weeks are Monday-to-Sunday in local dates, as the meal plan does (Task 7: `a DST week still has seven dates`; Task 9: `a run at 23:30 on Sunday matches that Sunday's plan`).

## Rulings (builder's calls the spec leaves open or that resolve gaps)

1. **Records only, no new protocol messages.** The phone has no coach socket. It reads and writes records only (`src/web/App.tsx`). So every run interaction is a `run` record, and the Mac uses the same records through `coach.tracking`. The coach owns `week-YYYY-MM-DD`, `status` and `review-YYYY-MM-DD`. People own `settings`, `manual-<uuid>` and `send-YYYY-MM-DD`. `src/shared/coach-protocol.ts`, the remote router and the change clock stay unchanged.
2. **Garmin confirmation is a record.** "As the existing upload flow does" cannot apply to the phone, so the confirm button writes `send-<week>` carrying the week's fingerprint. The coach sends only when that fingerprint equals the current plan's, and each send record is handled once (`garmin.confirmedMs`). This is the preview-and-confirm pattern of `GymCoach.preview/confirm`. The plan shown is the preview.
3. **Records are the source of truth.** Sent Garmin ids are kept in the week record, as the spec says. `coach/run/<id>.json` holds only a disposable cache (pace cache, attempts, last error). So a profile that moves to the server needs no new migration item: its records go with the account sync.
4. **Horizon.** On Sunday from 18:00 local time, the coming Monday's week is planned with `announce: true`. Switching on plans the rest of the current week from today with `announce: false`. The push goes only for `announce: true` weeks.
5. **Max heart rate.** "Highest value seen" means `max(GarminBody.maxHrSeen, max maxHr of run activities)`. "Else entered" means `profile.hrMaxBpm ?? profile.maxHrBpm`, since the profile has both fields. There is no age-based estimate: without a value, runs are planned by feel and by time, as the spec says.
6. **Bands and smoothing.** The easy band is 60 % to 75 % of max HR, and the cap is 75 %. The easy pace leaves out the first 300 s, seconds with |grade| > 3 % over a 30 s window, seconds with speed ≤ 0.5 m/s, and record gaps over 5 s. A run needs at least 300 easy seconds to count. The trend value at a time is the mean of the last 5 qualifying runs within 28 days before it, weighted by easy seconds. "4 and 12 weeks ago" are that value at now − 28 d and now − 84 d.
7. **Cross-sport load.** For the week being planned, take the bike and gym minutes (`rad` + `kraft` from `allTraining`) of the last complete week. Compare them with the mean of the 4 complete weeks before that. The excess cuts the run minutes, by at most 20 %.
8. **Bike and gym plans have no date.** The bike's `next.session` and the gym's `next.workout` are placed on the next usual bike or gym weekday (weekdays with at least 2 sessions in 28 days, as `usualTrainingDays` does) from the first plannable date on.
9. **Questionnaire pain.** "Pain while running: yes" plans like a healing complaint: half minutes and no test run. The text says only that the plan is gentle, with no diagnosis.
10. **Test value.** From a FIT file, the value is the best distance in any 1800 s window. A manual run on a test day takes its entered distance as the 30-minute distance, and the form labels it so. A Garmin run without a FIT gives no test value.
11. **Visibility.** The run tab, page, card, look back and push exist only once the `status` record says `on` or `suggest`. The "Laufen" switch in profile settings is always there, because switching on by hand must be possible without Garmin.
12. **The existing weekly view.** The phone has no weekly summary except "Gemeinsam", which compares people and so is ruled out. The look back is a `RunLookBack` section placed on the phone's "Verlauf" tab and the Mac's "Verlauf" page (HistoryView), both of which already show weeks.
13. **A missed run** replans the rest of the week and never adds its minutes to later days.
14. **The coach's sentence** on the run card is rule text. Claude adjusts only the weekly plan and may give a week note.
15. **Running days default.** Weekdays with at least 2 runs in the last 56 days. With none, Tuesday, Thursday and Saturday (`[1, 3, 5]`, Monday 0).
16. **One kinds list.** `RECORD_KINDS` moves to `src/shared/records.ts`. The five copies (`idbStore`, `webPort`, `records-api`, `web-server/records.ts`, and the `RecordKind` type) derive from it, so the next kind cannot be forgotten in one place.
17. **The spike** is Task 10's first step. The library check was already done on 2026-11-03 for 0.3.20. The bridge's `--check` mode runs at each coach start, and a failing check keeps the button out (`week.garmin = null`) while the rest ships.
